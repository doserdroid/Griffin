# Skill: Testing (TDD y pruebas de regresión)

Buenas prácticas técnicas genéricas para escribir y planificar tests, independientes de cualquier proyecto o framework de testing concreto.

- **Ciclo TDD**: red (test que falla) → green (mínimo código de producción para pasarlo) → refactor. Como tester, tu parte del ciclo es "red" (escribir el test que describe el comportamiento esperado) y validar "green" cuando el código llega.
- **Los tests unitarios son el grueso de la pirámide, no una categoría opcional.** Un test unitario prueba una única unidad de comportamiento (una función pura, un método de una entidad, un caso de uso) de forma aislada, sin red, sin base de datos real, sin reloj real. Reserva los tests de integración para el contrato entre una pieza y su dependencia externa real (un repositorio contra la base de datos, un adaptador contra una API) — son más lentos y más frágiles, así que deben ser los menos numerosos. Los tests end-to-end (flujo completo de usuario) son los más caros de mantener: solo los casos más críticos del negocio los justifican.
- **Diseña las unidades para que sean fáciles de testear de forma aislada**: funciones puras siempre que sea posible, dependencias inyectadas (por constructor o parámetro) en vez de importadas/instanciadas dentro de la unidad — así se pueden sustituir por test doubles sin trucos. Si una unidad es difícil de testear sin mockear medio sistema, es una señal de diseño a revisar, no solo un problema del test.
- **Estructura cada test en tres pasos reconocibles** (Arrange-Act-Assert / Given-When-Then): prepara el estado y las dependencias, ejecuta la acción bajo prueba, verifica el resultado. No mezcles preparación y aserciones intercaladas — un test que no se lee de arriba abajo en esas tres fases es más difícil de mantener.
- **Usa tests parametrizados/table-driven cuando varios casos comparten la misma lógica de aserción** con distintos datos de entrada (ej. varios valores límite de una validación) — evita duplicar el cuerpo del test para cada variante, siempre que la tabla siga siendo legible; si los casos difieren en algo más que el dato de entrada, es mejor separarlos en tests independientes.
- **Testea comportamiento observable, no implementación.** Evita aserciones sobre detalles internos (qué método privado se llamó, estructura interna de datos) salvo que sea parte del contrato público. Si refactorizas la implementación sin cambiar el comportamiento, el test no debería romperse.
- **Prioriza por valor**: lógica de negocio (casos de uso, entidades, validaciones) primero, luego integración (repositorios/adaptadores contra su contrato), y por último UI — ahí, solo lo esencial: renderizado condicional según estado, e interacciones clave del usuario.
- **Cobertura mínima por unidad de comportamiento**: camino feliz, al menos un caso límite (vacío, `null`/`undefined`, límite numérico, colección vacía...), y al menos un caso de error o validación fallida.
- **Test doubles en los límites del sistema**: mockea repositorios, servicios externos, reloj/fecha, red — nunca lo que estás probando, y evita mockear dependencias internas del propio dominio si se puede probar con datos reales en memoria.
- **Nombra los tests describiendo comportamiento**, no implementación ni número de caso: `"rejects an appointment without a client"` es mejor que `"test4"` o `"debería funcionar"`.
- **Un comportamiento por test.** Puede haber varias aserciones si validan el mismo comportamiento desde ángulos distintos, pero no mezcles comportamientos no relacionados en un mismo test.
- **Deterministas y aislados**: nunca dependas del orden de ejecución, de estado compartido entre tests, de la hora real del sistema o de red real.
- **Plan de pruebas de regresión**: para cada módulo/feature, documenta qué escenarios ya tienen test automático, cuáles no, y el riesgo de que un cambio futuro rompa algo sin que nadie se entere (alto/medio/bajo) — no es una lista de tests a escribir ya, es un mapa de dónde está la cobertura y dónde no.
